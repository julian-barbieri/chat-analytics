# AGENTS.md

Guía para agentes de código (Claude Code, Codex, Cursor, etc.) que trabajen en este repo. Para el uso como persona (API key, cómo correrlo, cron), ver [README.md](README.md).

## Qué es

`yt-monitor` (módulo `github.com/alphamedia/yt-monitor`): bot que **no escribe en YouTube** y monitorea comentarios y chat en vivo de canales de YouTube con una API key de la YouTube Data API v3. Es el primer bot del piloto de Alphamedia con **Radio Rivadavia** (canal `UCLAj5TzCrNbqe3LosSKHLcQ`, valor por defecto de `-canal`). `-canal` acepta varios canales: el primero es el principal y de los demás solo se siguen los vivos.

Dos modos, mismo binario:

- **Informe puntual** (`go run .`): baja videos recientes y vivos en curso, comentarios de las últimas N horas y opcionalmente N minutos de chat; escribe `informes/informe_<AAAA-MM-DD_HHMM>.md` y `informes/mensajes_<...>.csv` y termina.
- **Continuo con dashboard** (`go run . -dashboard :8080`): un worker consulta YouTube en bucle, persiste en `datos.jsonl` y un servidor HTTP sirve un dashboard con htmx que se refresca solo.

El bot **no publica, no modera y no usa OAuth**. Cualquier cambio que requiera escribir en YouTube (responder, borrar, moderar) es un cambio de alcance: consultarlo antes. El dashboard escribe en dos puntos, solo desde la PC del monitor (`sameOrigin` + `localRequest`): la configuración de canales e intervalos (`datos.canales.json`, ADR 0005) y pedir un análisis a Claude (cola).

Si se activa (`-claude-usd` > 0 y `CLAUDE_API_KEY`), el dashboard manda el **texto** de los mensajes de chat de cada programa (sin autores) a la API de Anthropic para resumirlos y agruparlos (ADR 0006). Sigue sin escribir en YouTube.

## Stack y restricciones

- Go puro, **solo biblioteca estándar**. `go.mod` no tiene `require` y debe seguir así; no agregar dependencias sin pedirlo.
- Cliente de la Messages API de Anthropic con `net/http` (`claude.go`), sin SDK.
- `go 1.24.7` en `go.mod` (se usa `min`/`max` built-in, patrones de ruta `GET /{$}` de `net/http` 1.22+, `http.FileServerFS`).
- Templates y JS se embeben con `//go:embed`: el binario es autocontenido. Al agregar archivos en `templates/` o `static/` revisar que las directivas `//go:embed` de `server.go` los cubran (`static/` solo embebe `htmx.min.js`).
- Frontend: `html/template` + htmx 2.0.4 vendorizado en `static/htmx.min.js` (no editarlo; no cargar nada de CDNs). CSS inline en `templates/layout.html` (encabezado común de las tres pantallas), sin frameworks ni JS propio.
- Plataformas objetivo: Linux y **Windows** (se compila `yt-monitor.exe` para una PC de la oficina). Por eso `main.go` importa `time/tzdata` (zonas del Pacífico y de Argentina); no sacarlo.

Lo mismo con Claude: `CLAUDE_BASE_URL=http://localhost:9998 CLAUDE_API_KEY=x ... -claude-usd 1` (`CLAUDE_BASE_URL` existe solo para pruebas y la vista previa).

Para ver el dashboard de una rama con los datos locales sin gastar cuota: `go run ./tools/preview -datos <ruta>/datos.jsonl` (ADR 0003). Compila la rama, la levanta en `http://localhost:8081` con el directorio de trabajo en una copia temporal de los datos y una API de YouTube y de Claude simulada (sin las claves reales), y `go run ./tools/preview -cortar` la corta y borra la copia. La vista previa copia `datos.jsonl`, `datos.cuota.json`, `datos.espectadores.jsonl`, `datos.vivos.jsonl` y `datos.analisis.jsonl` (ADR 0007) a la carpeta privada temporal; no copia `datos.claude.json` ni `datos.canales.json`. `-addr` solo acepta `localhost`, `127.0.0.1` o `::1`. Es el paso 7b de `/factory`: solo a pedido de la persona y siempre cortada antes de terminar.

**No correr `go run .` contra la API real sin que el usuario lo pida**: gasta cuota diaria compartida y escribe en `informes/`. El modo `-dashboard` además escribe en `datos.jsonl` y queda corriendo para siempre.

## Reglas del dominio (importantes)

### Cuota de la API

- 10.000 unidades por día por proyecto de Google Cloud; se reinicia a medianoche **del Pacífico** (`store.go: pacific`, `rollDay`). En Argentina eso es 04:00 o 05:00.
- Costos usados en el código (pasados a `get` como `cost`): `channels` 1, `playlistItems` 1, `videos` 1 cada 50 IDs, `commentThreads` 1 por página, `liveChat/messages` 5 por lectura, `liveChat/messages/stream` 5 por conexión (la cuenta `StreamChat` con `ChatBatch.Units`, no con `get`). Cada revisión de videos del worker gasta 3 (subidas + vivos + `videos`) más 1 por cada canal extra (solo su lista de vivos). La búsqueda rápida de un canal sin vivo (`ChannelLives`) gasta 2 por revisión (1 si su lista de vivos viene vacía), a lo sumo 40 por corte. Si se agrega un endpoint, poner su costo real según la documentación de YouTube (por ejemplo, `search.list` cuesta **100**: evitarlo).
- `YouTube.Units` se incrementa solo cuando hubo respuesta HTTP. En el worker, todo llamado a la API debe ir envuelto en `spend(...)` para que se sume a `Store.AddUnits`. La excepción es `StreamChat`, que corre en otra goroutine: no toca `Units` y avisa la cuota en el primer `ChatBatch` (5 al haber respuesta HTTP), que el worker suma al procesarlo.
- El worker deja de leer el chat al llegar a `Budget - reserveForComments` (1.500 de reserva) y deja de consultar todo al llegar a `Budget` (`-cuota`, 9.000 por defecto). Cada canal tiene su intervalo de chat (pico y fuera, dentro de `-pico`, 7-20 hora local) entre dos conexiones o lecturas de sus vivos; con varios vivos del mismo canal se turnan. Cada canal suma su propio chat a la cuota. Entre canales, una sola acción de chat por vuelta del worker: nunca dos lecturas comunes en paralelo. Los vivos de `-vivos` que no son de un canal configurado usan `-chat-seg-pico` / `-chat-seg` (`WorkerConfig.chatInterval`). Sin `datos.canales.json` cada canal arranca con `-chat-seg-pico` (60 s) × N y `-chat-seg` (180 s) × N, el mismo gasto que cuando todos se turnaban con un solo intervalo; con `WorkerConfig.Settings` en `nil` (modo informe, tests) hay un solo grupo, como antes. Agregar un canal cuesta 1 unidad al resolverlo (`spend`) y ~480 por día de revisión de sus vivos. Con el vivo de 24 horas entra en el día: ~1.440 de videos + ~1.000 de comentarios + ~5.000 de chat (3.900 + 1.100). Cada canal extra suma ~480 de videos y, si abre un vivo por programa, hasta ~240 de búsqueda rápida (6 cortes × 40): con un canal así son ~8.160 y no entra en las 7.500 del chat (las cuentas, en el README; se arregla subiendo intervalos en Canales, que muestra la barra antes de guardar); el chat de un canal cuesta lo mismo con uno o varios vivos porque se turnan. Ejemplo por canal (`TestEstimateQuota`): Rivadavia 2 / 5 min 24 h y Rock & Pop 3 / 5 min 18 h dan 1.920 + 1.000 + 2.610 + 1.600 = 7.130. Si se pasa, el chat se pausa al final del día del Pacífico, que en Argentina es la madrugada.
- Los comentarios solo se piden para videos cuyo `commentCount` cambió (`knownComments`). Mantener ese tipo de ahorro en cualquier cambio.
- Si un cambio altera el consumo, recalcular y actualizar las cifras de cuota del README.

### Análisis con Claude

- Apagado por defecto. Se activa con `-claude-usd` (tope diario en dólares, día local, contador en `datos.claude.json`) y `CLAUDE_API_KEY`. Un pedido por programa al terminar y otro por botón como mucho cada 10 min por canal. Nunca se manda un pedido cuyo peor caso pase el tope. Se manda solo el texto y la hora de los mensajes de chat, sin `Author`, sin IDs y sin los que `Classify` marca como spam. Los conteos se hacen en Go; del modelo solo se usan textos y números de mensaje validados. Modelo por defecto `claude-sonnet-5-5` (`-claude-modelo`); si se agrega un modelo, poner su precio real en `claudePrices`. Si cambia el costo, actualizar las cifras del README.
- Salida estructurada con `output_config.format` y `effort: "low"`; no mandar `tool_choice` forzado, `thinking`, `temperature`, `top_p`, `top_k` ni prefill de `assistant` (dan 400).
- El peor caso (`claudeWorstCase`) cuenta la salida completa hasta `claudeMaxTokens` (el thinking se cobra como salida) y el escalón de Haiku; el costo real (`claudeCost`) usa el `model` de la respuesta y, si no está en la tabla, el precio más caro. Errores: 401 / 403 / 404 apagan el análisis hasta reiniciar; 400, 413, respuesta que no se entiende, `refusal` y `max_tokens` se guardan sin reintentar; 429 / 5xx / red se reintentan dos veces (`claudeRetryWaits`, o `retry-after` si es mayor). Nada de reintentos agresivos. Si el pedido salió y no volvió `usage` (`ClaudeReply.MaybeBilled`: timeout, corte, respuesta ilegible), se suma el peor caso al gasto. El cliente no sigue redirecciones y tapa la clave antes de cortar cualquier texto.

### Vivos y programas

- Radio Rivadavia tiene **un solo vivo de 24 horas** que empezó hace días y queda fuera de los últimos `-videos` subidos. `ChannelVideos` lo encuentra con la lista automática de vivos del canal: el ID de la lista de subidas con `UU` cambiado por `UULV`. No está documentada; si falla, se sigue sin ella, y `-vivos` permite agregar videos a mano.
- No usar `search.list` con `eventType=live` para detectar vivos: cuesta 100 unidades.
- El título del vivo cambia con cada programa. Los mensajes de **chat** guardan el programa en `Message.Program` al recibirse (`TagProgram`, con `ProgramName`, que saca el canal del título: adelante como en Rivadavia, "… en VIVO | PROGRAMA", o atrás como en Rock & Pop, "🔴 [EN VIVO] PROGRAMA | ROCK & POP", comparando con `Video.Channel`; un "| EN VIVO" final, como en Luzu TV, se descarta). Si se suma un canal con otro formato, agregar el caso a `TestProgramName`. Los comentarios no tienen programa. `programOf` cae al título actual del vivo para mensajes de chat guardados antes de que existiera el campo.
- En el dashboard el chat llega **en tiempo real** por streaming (`StreamChat`): una conexión abierta por vivo, 5 unidades cada vez que se abre. Lo pidió el usuario para ver los mensajes sin demora. El intervalo es por canal (el de `Settings`: pico y fuera) y es el mínimo entre dos conexiones o lecturas de los vivos de ese canal, así que si YouTube corta seguido las conexiones el gasto no supera al de las lecturas por turnos. `chatInterval` (`-chat-seg-pico` / `-chat-seg`) vale para los vivos sueltos de `-vivos` que no son de un canal configurado (grupo `""`, que suma su propio chat a la cuota) y para el modo sin `Settings` (informe, tests), donde todos los vivos son un solo grupo. Si el streaming de un chat da 403 (que no sea de cuota) o 404, se marca `noStream` y ese chat vuelve a leerse por turnos con `LiveChatPage`; si ahí también da 403, queda `blocked`.
- Las lecturas comunes (`LiveChatPage`) van **por turnos** (`nextChat`: el del canal más atrasado y, dentro del canal, el que hace más tiempo que no se lee; una por vuelta). `LiveChats` hace lo mismo en el modo informe. No hacer lecturas comunes en paralelo: duplica la cuota y el cliente no es concurrente.
- De los canales extra solo se guardan los vivos en curso o programados (`ChannelVideos` descarta el resto) para no gastar cuota en comentarios de sus videos viejos.
- Búsqueda rápida: cuando un canal se queda sin vivo, se revisa solo ese canal (`ChannelLives`, 2 unidades con `spend`) cada 1 min (`fastEvery`) durante 20 min (`fastFor`), nunca en el mismo tick que la revisión completa ni con el tope `Budget` alcanzado; si aparece un vivo, se abre su chat sin esperar la revisión de 3 min. Después, cada 3 min con el resto. Gasta a lo sumo 40 unidades por corte.
- Cada video sabe de qué canal es por `Video.ChannelID` (`snippet.channelId`, en la misma parte que ya se pide; si no viene, `ChannelVideos` y la búsqueda rápida lo completan según la lista del canal en la que apareció, sin cuota extra). La vista por canal depende de eso: un canal dado como @handle se asocia por el ID que devuelve `LookupChannel` (`items[0].id`).

### Chat en vivo

- Respetar `pollingIntervalMillis` que devuelve YouTube (el worker usa `max(wait, cfg.ChatEvery)`; `LiveChat` usa al menos 10 s).
- Puede que YouTube rechace leer el chat con API key sola (403/401). En ese caso el worker marca `blocked` en el `chatState` de ese vivo y no insiste; si el error menciona `quota`, sí reintenta. No convertir eso en reintentos agresivos.
- El token de página del chat es por vivo (`chats`, un `chatState` por ID); cuando un vivo termina se cancela su streaming y se olvida su estado. El streaming se retoma con el último `nextPageToken` recibido, así que no se pierden mensajes al reconectar. Si no llega nada en `streamIdle` (5 min), `StreamChat` corta la conexión para reabrirla.

### Datos y privacidad

- Políticas de YouTube: **no guardar datos de la API más de 30 días** (`retention` en `store.go`). `OpenStore` descarta lo vencido y reescribe el archivo. No alargar esa retención ni agregar otros almacenamientos que la salteen.
- `datos.espectadores.jsonl` guarda cuántos miraban cada vivo en cada revisión de videos (`ViewerSample`). Son datos de la API: misma retención de 30 días al abrir (`loadViewers`, tmp + `os.Rename`) y nunca dentro de `datos.jsonl`, para no cambiar el formato de `Message`. Está en `.gitignore` (`datos.*.jsonl`).
- `datos.vivos.jsonl` guarda una muestra por vivo en curso en cada revisión de videos y en cada búsqueda rápida (`LiveSample`: hora, ID del vivo, ID y nombre del canal, título): datos de la API, misma retención de 30 días al abrir (`loadJSONL`, tmp + `os.Rename`), nunca dentro de `datos.jsonl`. Se guarda el título y no el programa, para que una mejora de `ProgramName` valga también para lo guardado. Está en `.gitignore` (`datos.*.jsonl`).
- `datos.canales.json` guarda solo lo que escribió la persona en Canales (canales como `Input`, intervalos y pausas), nada de la API: el nombre y el ID resueltos quedan en memoria (`ChannelStatus`). Se escribe con tmp + `os.Rename` (`Settings.Update`); si existe, gana sobre `-canal` y `-chat-seg*` (se avisa si se pasaron a mano); si no se entiende, el monitor no arranca y no se pisa. Está en `.gitignore` (`datos.*.json`). La vista previa no lo copia.
- `datos.analisis.jsonl` guarda los análisis de Claude (textos del modelo e IDs de mensajes de ejemplo, no sus textos): misma retención de 30 días al abrir contada desde el mensaje más viejo analizado, tmp + `os.Rename`, nunca dentro de `datos.jsonl`. `datos.claude.json` guarda solo el gasto del día.
- `datos.jsonl` e `informes/` contienen nombres de usuarios y mensajes reales: son datos generados, no código. No editarlos a mano, no usarlos como fixtures de tests (los tests arman sus propios datos) y no subirlos a ningún lado.
- La única copia permitida de los datos es la temporal de la vista previa (`tools/preview`, que copia `datos.jsonl`, `datos.cuota.json`, `datos.espectadores.jsonl`, `datos.vivos.jsonl` y `datos.analisis.jsonl`, y no `datos.claude.json` ni `datos.canales.json`): una carpeta `yt-monitor-vista-previa-*` con permisos `0700` dentro de una carpeta privada del usuario (`os.UserCacheDir()/yt-monitor-vista-previa/`, también `0700`; en Linux, `~/.cache/yt-monitor-vista-previa/`), nunca en la carpeta temporal compartida. Se borra al cortarla, y la siguiente vista previa barre al arrancar las copias huérfanas que hayan quedado (por ejemplo, si se apagó la máquina). El dashboard le aplica la misma retención de 30 días al abrirla. Nunca se usa en tests: los de `tools/preview` arman datos sintéticos en `t.TempDir()`.
- `.env` tiene `YT_API_KEY` y `CLAUDE_API_KEY`. **No leer, imprimir ni commitear su contenido.** Las claves nunca deben aparecer en logs, errores ni en el dashboard: `YouTube.get` la reemplaza por `***` en errores de red; `Claude` manda la clave solo en `x-api-key` y la reemplaza por `***` en cualquier error. Mantener ese cuidado en cualquier código nuevo que formatee URLs o errores.
- El dashboard no tiene autenticación. Por defecto escucha en `localhost`; no cambiar ese default ni sugerir exponerlo a internet.

### Formato de `Message` y CSV

- `datos.jsonl`: un `Message` por línea, con los nombres de campo de Go (`ID`, `Source`, `VideoID`, `Author`, `Text`, `At`, `Likes`, `Replies`, `Program`). Los Super Chats y Super Stickers suman `Super` (`"superchat"` o `"supersticker"`), `AmountMicros`, `Currency`, `AmountText`, `Tier` y `Sticker`, todos con `omitempty` para que las líneas comunes no cambien. Cambiar nombres o tipos de campos rompe la carga de datos ya guardados; si hace falta, que sea compatible hacia atrás.
- Los montos de Super Chat son **brutos**, en la moneda de quien pagó: se suman por moneda en `int64` de micros y nunca se convierten ni se mezclan monedas. No son lo que cobra el canal (eso requiere OAuth, fuera de alcance).
- `Source` vale `"comentario"` o `"chat"` (en español; el dashboard y los informes dependen de esos valores).
- La categoría **no se guarda**: se calcula con `Classify` cada vez que se lee. Cambiar el clasificador re-clasifica todo el histórico, lo cual es intencional.
- El CSV (informe y `GET /export.csv`) se arma con `csvHeader` y `csvRow` en `main.go`: `fuente, fecha, video, programa, autor, categoria, likes, respuestas, texto, pago, monto, moneda, monto_youtube, nivel, sticker` (las 6 últimas vacías en mensajes comunes; columnas nuevas siempre al final). Está pensado para subirlo a Claude.

### Clasificador

- Orden de prioridad en `Classify`: spam (links, teléfonos, palabras de spam) > insulto > pregunta > queja > elogio > mayúsculas sostenidas (insulto) > otro. El orden importa: un mensaje con link y signo de pregunta es spam.
- Es un primer filtro barato y deliberadamente simple; el análisis fino lo hace Claude sobre el CSV. Lo mismo vale para `analyze.go`: las frases de `techIssues` se buscan como frases enteras sin tildes (`phraseText`); no agregar palabras sueltas que en una radio de noticias suelen ser tema ("audio", "corte", "retraso"). Cubrir los casos en `TestTechIssue` y `TestAnalyze`. `classify.go` y `analyze.go` siguen siendo solo reglas y funciones puras: no meter llamadas a LLMs ahí. El análisis con Claude vive aparte (`claude.go`, `analyst.go`), no reemplaza a `Classify` y la categoría de reglas sigue siendo la única del CSV y de 'Categorías de hoy'.
- Las listas comparan contra el texto en minúsculas con `strings.Contains`, así que una palabra corta puede matchear dentro de otra (por ejemplo `"lag"`). Al agregar términos, pensar en falsos positivos en español rioplatense y cubrirlos en `TestClassify`.
- Las constantes `Cat*` son también las claves de CSS (`.badge.spam`, etc.). Si se agrega una categoría, sumarla a `categories` y `catLabels` en `server.go`, al bucle de `report` en `main.go` y, si corresponde, al CSS.

## Concurrencia

- Hay una sola goroutine que hace las llamadas comunes a YouTube (`RunWorker`); el cliente `YouTube` **no es seguro para uso concurrente** (`Units` sin lock). No llamarlo desde handlers HTTP. Las goroutines de streaming solo usan `StreamChat`, que lee `Key`, `BaseURL` y `Stream` sin modificarlos, y no tocan `chats` ni `lives`: todo lo que reciben se lo pasan al worker por el canal `events`.
- Los handlers solo leen el estado vía `Store.Snapshot()`, `Store.Status()`, `Store.LastChat()`, `Store.LastChatOf()`, `Store.Viewers()`, `Store.Lives()`, `Store.MessagesOf()`, `Store.Analyses()` o `Store.FirstLive()`, que devuelven copias (o, en `Analyses`, análisis que no se modifican después de guardarlos). No exponer los slices internos del `Store` ni modificar el `Store` desde el servidor.
- `Settings` (`datos.canales.json`) es lo único de la configuración que escriben los handlers: con su mutex, fuera del `Store`, solo con `Settings.Update` y detrás de `sameOrigin` y `localRequest`. Los handlers nunca llaman a YouTube ni escriben en el `Store`: un canal agregado queda "resolviendo…" hasta que el worker lo resuelve (1 unidad con `spend`) o anota que no existe. El worker lee `Settings` en cada tick (`Get`, copia + versión).
- `RunAnalyst` es la única goroutine que usa el cliente `Claude` (no es concurrente). Lee el `Store` con copias y escribe solo los análisis, el gasto y su estado. Los handlers no llaman a Claude: el botón solo encola con `Analyst.Request`, detrás de `sameOrigin` y loopback. Los handlers leen los análisis con `Store.Analyses()`.
- `Store.Add` agrega al JSONL en modo append; la compactación (`rewrite`) solo ocurre al abrir. Si se agrega limpieza periódica, hacerla bajo el lock y con el patrón archivo temporal + `os.Rename`.

## Estilo

- **Todo en español**: comentarios, mensajes de log, errores al usuario, textos del dashboard, nombres de flags (`-horas`, `-cuota`) y de categorías. Identificadores de Go en inglés como hasta ahora (`Store`, `Classify`, `RunWorker`). Español rioplatense con voseo en textos para el usuario ("Abrí", "ponela").
- Código corto y directo, como el existente: funciones chicas, structs anónimos para decodificar JSON de la API, `map[string]any` para datos de templates, comentarios breves que explican el *por qué* (cuota, políticas de YouTube), no el *qué*.
- Errores: en el modo informe, los fatales usan `check(err)`; los recuperables (video con comentarios desactivados, chat rechazado) se loguean como `aviso:` y se sigue. En el worker, nunca terminar el proceso: loguear, guardar en `SetError`/`SetChatNotes` y reintentar más tarde.
- Fechas visibles en hora local (`t.Local()`). `main` fija `time.Local` con `-zona` (por defecto `America/Argentina/Buenos_Aires`, vía `setZone`) antes de arrancar goroutines, porque la PC o WSL pueden estar en UTC: no depender de la zona del sistema. Formato `2006-01-02 15:04` en CSV/informes y `02/01 15:04` en el dashboard. Números con separador de miles `.` vía `miles`.
- Dashboard: tres pantallas con el mismo encabezado y pestañas (`templates/layout.html`); links comunes entre pantallas y htmx para los parciales, sin JS propio. Botones, pestañas y campos de al menos 44 px de alto. Usar los tokens CSS (`--surface-*`, `--text-*`, `--series-1..5`, `--link`, `--sent-*`, `--ia-*`, `--field-border`, `--on-accent`, etc.) y definir cualquier color nuevo en ambos temas; `TestTemplateTokens` lo controla, y los `style="…"` de las plantillas solo llevan valores calculados (`width`, `left`, `flex-grow`), nunca colores. Los títulos de las tarjetas no van numerados. Lo plegado va en `<details>`; para que siga abierto después del refresco, el estado viaja en el parámetro `abrir` (lista cerrada, `foldSections`) como `ver` y `horas`, sin JS propio: un input oculto `.vq`, el `hx-get` del refresco y un `hx-get` en cada `<summary>` con su sección cambiada. Nunca reflejar en el HTML un valor de `abrir` que no esté en la lista. Mantener los atributos de accesibilidad (`aria-label`, `role="img"`, `<title>` en barras). `html/template` ya escapa: no usar `template.HTML` con texto de usuarios.
